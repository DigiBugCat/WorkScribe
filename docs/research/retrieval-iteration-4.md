# Iteration 4: retrieval funnel

This branch owns transcript retrieval; indexed-vault integration is the separate `e4b-vault` job. `RetrievalConfig.application()` defaults to a broad funnel: 30-word ungrouped units, 0.85 cosine / 0.15 BM25, a 0.1 typing-time boost, 50 seed units, five seconds of neighboring context, and twelve seconds of following answers for question jots. `RetrievalConfig()` retains the old policy for reproducible controls. These initial application knobs are provisional; the sweep writes measured deployment candidates separately.

`NotePlanner.rank` searches every available small unit without lexical question-coverage or cosine yes/no gates. `expand` follows ranked seeds, deduplicates units, and returns transcript order to the writer. Every original chunk/segment ID stays attached. `NotePlan.limitPromptTokens` removes weakest evidence until the full E4B per-note prompt (including template and BOS) fits the configured cap. Runtime uses the tokenizer vocabulary already inside the E4B GGUF, opened with `vocab_only` on CPU; no model weights, inference context or GPU allocation is needed. The evaluator now uses the same native counter exclusively. Tests check its counts against the saved independent tokenizer corpus and the actual generation prompt statistics. Zero disables this cap for the explicit whole-transcript diagnostic only. The cap applies to transcript per-note generation; image, topics and action calls are separate existing paths.

The existing 0.68 relevance gate remains downstream, owned by `e4b-decision`; retrieval does not try to decide answerability. Query rewrites are never writer evidence. `--expand-retrieval-queries cases.jsonl cache.json` runs only local resident E4B/llama.cpp, with no transcript/gold in the rewrite prompt, checkpoints each completed exact jot text, and skips cache hits. `WORKSCRIBE_QUERY_EXPANSIONS=cache.json` enables the cache in the app / notes eval. `--query-expansions cache.json` enables it in retrieval evaluation and embedding-cache filling. Extra vectors retain the query role, and each document gets its best original-or-rewrite cosine before the BM25 blend. No expansion benefit is claimed before the orchestrator creates that cache and reruns the sweep.

## Evaluation

`scripts/sweep-retrieval-4.py` evaluates the actual Swift selector and full E4B tokenizer, then chooses size/window knobs on eleven cases (typing-time boost fixed at 0.1 by default; `--time-weights` enables a separate ablation) and scores the twelfth, repeated for all twelve cases. Families are embedding-only, hybrid and BM25-only at 450, 1500 and 4000 full prompt tokens. Selection objective is case-balanced macro recall minus 0.03 times empty-gold abstain false-match rate. False matches are lightly penalized because the decision stage handles them. Baseline and whole-transcript are fixed controls. Whole-transcript uses up to 512-word same-speaker groups to reduce XML wrapper overhead without dropping source words; the bounded ranker uses the swept small units. Recall@10/25/50 measures gold *segment* coverage by the top K ranked small units, without expansion or cap; gold span/chunk labels do not exist. Their reported full-prompt costs are diagnostic and can exceed 4000. Bounded selection recall includes expansion and cap.

The generated `context-*.json` files are fit on all cases **after** held-out evaluation; they are deployment candidates, not independent test results. `result.json` records exact case, binary, tokenizer, embedding cache and optional expansion-cache hashes. Cache misses fail; vectors are never silently replaced by BM25. `--retrieval-cache-misses ... --config ... --embed-cache ... --out misses.json` exports exact role-tagged missing inputs without model access.

## Late chunking: feasibility only

Inspected the pinned FluidUse `d278e17df85e39e8c21bb64a467da81c39576fcd` manager and WorkScribe's manifest pinning Core ML text artifact `70fcf18f32c8cffc173fea982d5652d0bd1de8ea`; checked the exporter's declared graph I/O. No Core ML graph was loaded in this sandbox. The Swift manager exposes only normalized 768-dimensional pooled vectors, not token states; `embed_32/48/64/128/256/512` have `embedding [1,768]` output. The wrapper truncates the **prefixed** input including BOS/EOS at 512 tokens. `hidden_size=512` is not the output dimension.

A useful narrow exception: the existing `pack_256` function takes `attention_bias [1,1,256,256]`, `positions [256,1]`, and an arbitrary `pool [8,256]`, and emits eight pooled vectors. The current wrapper blocks attention between independent texts and resets positions. A 256-token late-chunking prototype could instead supply contiguous positions, a joint padding-only attention mask, and eight span-pooling rows. This does not expose token states but may yield contextualized span vectors without re-export. It requires a new wrapper and parity/position/padding tests; it has **not** been implemented or measured here.

For explicit token states or a useful 1k–8k joint window, re-export is required: preserve pre-pooling contextual states, expose `[1,S,512]` (or the correct projected token stage), then reproduce the original pooling/projection/normalization order for each span. Use fixed shapes, validate document/query-prefix handling and span offsets, and compare to a full-precision reference before ANE latency/memory tests. The upstream model card advertises an **8192-token supported window**. The config's 262144 maximum-position value is not a validated operating window; its sliding-window setting also differs from the prose card. Do not infer long-window quality or ANE placement from those declarations.

Engineering estimate, not measured: 0.5–1 day for a 256-token pack-wrapper feasibility/parity probe; 1–2 days for token-output re-export and numerical parity; another 1–3 days for fixed longer-shape conversion, correct sliding/full attention masks, ANE placement, memory/latency and retrieval evaluation. Longer graphs may move ops to CPU/GPU; no residency or speed claim.

## Integration with the parallel jobs

The decision job owns downstream relevance/answerability, including the old 0.68 gate; this patch deliberately leaves that gate alone. The vault job should combine its selected evidence with the transcript plan **before** applying `RetrievalBudget.apply`, so the 4k limit covers the combined writer prompt. In particular, appending vault context after `NoteEnhancer.selection` returns would bypass this cap. Preserve each source's provenance while deduplicating and presenting the final set chronologically. `NoteEnhancer.selection`, `RetrievalConfig`, `Entry`, and `NoteEvaluation` are likely merge overlaps.

The tests that exercise mock generators now pass an explicit legacy `RetrievalConfig()` instead of accidentally loading the new application's real embedding ranker. The default app selects `RetrievalConfig.funnel()`; environment-supplied config files still load their explicit overrides against the reproducible legacy defaults. No installed app, model files, vault, or other clone was changed.
